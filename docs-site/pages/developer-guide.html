Project Overview

Automergent is an AI-powered coding agent that lives in your terminal. It provides a full-featured TUI built with the Charm v2 stack, supports multiple AI providers, and ships with 43+ built-in tools across 13 categories.

Prerequisites

You need Go 1.25+ with CGO enabled. Some features (tree-sitter parsing, SQLite) require CGO. On macOS, ensure Xcode command line tools are installed. On Linux, you may need gcc and the SQLite development headers.

Building

Automergent uses a Makefile with standard targets. All build commands require CGO_ENABLED=1.

Make Targets

CommandDescription
make buildBuild the binary to bin/automergent
make installInstall to $GOPATH/bin
make testRun all tests (CGO_ENABLED=1 go test ./...)
make lintRun golangci-lint
make fmtFormat with gofmt + goimports
make tidyRun go mod tidy
make ciFull CI checks locally (test + vet + lint)
make cleanRemove bin/ directory
make releaseRun GoReleaser snapshot build

Build Flags

The build injects version metadata via ldflags:

makefile 
LDFLAGS_AUTOMERGENT := -s -w \
  -X 'github.com/iSundram/Automergent/internal/version.Version=$(VERSION)' \
  -X 'github.com/iSundram/Automergent/internal/version.Commit=$(COMMIT)' \
  -X 'github.com/iSundram/Automergent/internal/version.BuildDate=$(BUILD_DATE)'

These values are read at runtime by the internal/version package and displayed via automergent --version.

CI/CD Pipeline

Automergent uses GitHub Actions for continuous integration and GoReleaser for release distribution.

Continuous Integration

CI runs on every pull request and push to main. The pipeline performs:

  • Tests — CGO_ENABLED=1 go test ./...
  • Vet — go vet ./...
  • Lint — golangci-lint run ./...
yaml .github/workflows/ci.yml 
name: CI
on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version: "1.25"
      - run: CGO_ENABLED=1 go test ./...
      - run: go vet ./...
      - run: golangci-lint run ./...

Release Pipeline

Releases are triggered by pushing a v* tag (e.g., v1.0.0). GoReleaser builds binaries for:

Testing

All tests require CGO enabled. Run the full suite with:

CGO_ENABLED=1 go test ./...

Test Patterns

The codebase uses several testing strategies:

  • Table-driven tests — standard Go pattern for input/output assertions
  • Mock providers — in-memory provider implementations for testing agent behavior
  • Debug provider — the internal/debug package provides a decorator that logs all requests/responses, useful for isolated testing
  • Session testing — the internal/session package supports in-memory sessions for testing without disk I/O
  • Tool testing — tools implement a common interface; tests can exercise them with mock contexts and file systems
  • Concurrency testing — the tool registry and agent event bus are tested for concurrent access safety

Running Specific Tests

bash 
# Run tests in a specific package
CGO_ENABLED=1 go test ./internal/tools/...

# Run tests matching a pattern
CGO_ENABLED=1 go test -run TestTool ./internal/tools/

# Run tests with verbose output
CGO_ENABLED=1 go test -v ./internal/agent/...

# Run tests with race detection
CGO_ENABLED=1 go test -race ./...

Linting

Install golangci-lint and run:

golangci-lint run ./...

The project uses the default golangci-lint configuration. CI will fail if any lint errors are found.

Key Interfaces

Automergent is built around a few core interfaces. Understanding these is essential for contributing new tools, providers, or themes.

Tool Interface

Every tool must implement the Tool interface defined in internal/tools/tool.go:

go internal/tools/tool.go 
type Tool interface {
    Name() string
    Description() string
    Schema() map[string]any
    Execute(ctx context.Context, args map[string]any) (Result, error)
    RequiresConfirmation(mode string) bool
    IsConcurrencySafe(args map[string]any) bool
    IsReadOnly(args map[string]any) bool
    IsDestructive(args map[string]any) bool
    EstimatedCost() ToolCost
}
MethodPurposeDefault
Name()Unique tool identifier used in schemas and logs—
Description()Shown to the AI model in tool schemas—
Schema()JSON Schema for the tool's parameters—
Execute()Run the tool with the given arguments—
RequiresConfirmation()Whether this tool needs user approval before runningfalse
IsConcurrencySafe()Whether the tool can run concurrently with othersfalse
IsReadOnly()Whether the tool only reads (no side effects)false
IsDestructive()Whether the tool can destroy datafalse
EstimatedCost()Token and latency estimates for schedulinglow cost

BaseTool Helper

Embed BaseTool to get safe defaults for the boolean methods and cost estimates:

go 
type MyTool struct {
    tools.BaseTool
}

func (t *MyTool) Name() string        { return "my_tool" }
func (t *MyTool) Description() string  { return "Does something useful" }
func (t *MyTool) Schema() map[string]any {
    return map[string]any{
        "type":       "object",
        "properties": map[string]any{...},
        "required":   []string{...},
    }
}
func (t *MyTool) Execute(ctx context.Context, args map[string]any) (tools.Result, error) {
    // implementation
}

Provider Interface

AI providers implement the Provider interface from internal/ai/provider.go:

go internal/ai/provider.go 
type Provider interface {
    Name() string
    Complete(ctx context.Context, req CompletionRequest) (CompletionResponse, error)
    Models(ctx context.Context) ([]Model, error)
    TokenCount(messages []Message) (int, error)
    ContextLimit() int
}

RetryObserver Interface

Providers that retry internally can implement RetryObserver to report retry attempts to the UI:

go 
type RetryObserver interface {
    SetRetryObserver(func(RetryInfo))
}

Wrapping providers (caching, debug, etc.) must forward this to the wrapped provider so retries remain visible.

Adding a New Tool

New tools are the most common contribution. Follow these steps to add one:

Step 1: Create the tool file

Add a new file in the appropriate internal/tools/<category>/ directory:

go internal/tools/mytool/mytool.go 
package mytool

import (
    "context"

    "github.com/iSundram/Automergent/internal/tools"
)

// MyTool implements tools.Tool
type MyTool struct {
    tools.BaseTool
}

func (t *MyTool) Name() string { return "my_tool" }

func (t *MyTool) Description() string {
    return "Description shown to the AI model"
}

func (t *MyTool) Schema() map[string]any {
    return map[string]any{
        "type": "object",
        "properties": map[string]any{
            "input": map[string]any{
                "type":        "string",
                "description": "The input parameter",
            },
        },
        "required": []string{"input"},
    }
}

func (t *MyTool) Execute(ctx context.Context, args map[string]any) (tools.Result, error) {
    input, _ := args["input"].(string)

    // Tool logic here

    return tools.Result{
        Content: "Result text",
        Summary: "Short summary for UI",
    }, nil
}

Step 2: Register the tool

In cmd/automergent/main.go, add the import and register the tool in the tool registry setup block:

go cmd/automergent/main.go (excerpt) 
import (
    toolsMyTool "github.com/iSundram/Automergent/internal/tools/mytool"
)

// In the tool registry setup:
reg.Register(&toolsMytool.MyTool{})

Step 3: Add a tool prompt (optional)

Add a prompt file in internal/prompt/phases/ to guide the model on when and how to use your tool.

Step 4: Test

Write tests in mytool_test.go following the table-driven test pattern:

go 
func TestMyTool(t *testing.T) {
    tool := &MyTool{}

    if tool.Name() != "my_tool" {
        t.Errorf("expected name my_tool, got %s", tool.Name())
    }

    result, err := tool.Execute(context.Background(), map[string]any{
        "input": "test",
    })

    if err != nil {
        t.Fatal(err)
    }
    if result.IsError {
        t.Error("expected success")
    }
}

Adding a New Provider

New AI providers implement the Provider interface and register themselves in the global provider registry.

Step 1: Create the provider package

go internal/ai/myprovider/myprovider.go 
package myprovider

import (
    "context"
    "github.com/iSundram/Automergent/internal/ai"
)

type Provider struct {
    config ai.ProviderConfig
}

func New(cfg ai.ProviderConfig) *Provider {
    return &Provider{config: cfg}
}

func (p *Provider) Name() string { return "myprovider" }

func (p *Provider) Complete(
    ctx context.Context,
    req ai.CompletionRequest,
) (ai.CompletionResponse, error) {
    // Call your provider's API here
    // Return a CompletionResponse with streaming support
}

func (p *Provider) Models(ctx context.Context) ([]ai.Model, error) {
    // Return available models
}

func (p *Provider) TokenCount(messages []ai.Message) (int, error) {
    // Estimate token count
}

func (p *Provider) ContextLimit() int {
    return 128000 // context window size
}

Step 2: Register in the provider catalog

Add your provider to internal/config/providers_catalog.go so it appears in the config schema and auto-discovery:

go 
// In the catalog entry:
"myprovider": {
    Name:        "myprovider",
    DisplayName: "My Provider",
    EnvKey:      "MYPROVIDER_API_KEY",
    Models:      []string{"model-1", "model-2"},
    DefaultModel: "model-1",
}

Step 3: Wire into the CLI

In cmd/automergent/main.go, add a case in the provider switch:

go 
case "myprovider":
    provider = myprovider.New(aiCfg)

Step 4: Configure

Add to your ~/.automergent/config.yaml:

yaml 
provider: custom
model: model-1

providers:
  custom:
    apiKey: "your-api-key-here"
    baseUrl: "https://your-endpoint/v1"
    defaultModel: "model-1"

Debug Mode

Automergent includes a debug provider that wraps any AI provider to log all requests and responses. This is invaluable for understanding model behavior and debugging prompt issues.

How It Works

When debug mode is enabled, the DebugProvider wraps the primary provider as a transparent decorator:

go internal/debug/provider.go 
type DebugProvider struct {
    provider ai.Provider
    logger   *Logger
}

func (d *DebugProvider) Complete(
    ctx context.Context, req ai.CompletionRequest,
) (ai.CompletionResponse, error) {
    start := time.Now()
    d.logger.LogRequest(ctx, d.provider.Name(), req)

    resp, err := d.provider.Complete(ctx, req)

    if err != nil {
        d.logger.LogError(ctx, d.provider.Name(), err, req)
        return nil, err
    }

    d.logger.LogResponse(ctx, d.provider.Name(), resp, time.Since(start))
    return resp, nil
}

Enabling Debug Mode

Add to your config or use the CLI flag:

yaml ~/.automergent/config.yaml 
debug:
  enabled: true
  output_dir: "./debug-logs"

Or via environment variable:

export AUTOMERGENT_DEBUG_ENABLED=true

What Gets Logged

  • Requests — full CompletionRequest including messages, tools, and system prompt
  • Responses — completion response with token usage and latency
  • Errors — error details with request context
  • Retries — retry attempts via the RetryObserver interface

Architecture

The debug wiring in cmd/automergent/main.go shows the decorator chain:

go 
// Provider resolution chain:
provider := googleProvider.New(aiCfg)    // base provider
provider = cache.NewCachingProvider(...)  // optional caching wrapper
provider = debug.NewDebugProvider(...)    // debug wrapper (outermost)

The debug provider also implements Unwrap() to let callers reach the underlying provider's capabilities.

Additional Notes

Session Persistence

Automergent persists conversation sessions to disk using JSONL format. The session system supports:

  • Crash recovery via state.json and recovery.json
  • Auto-save every 30 seconds
  • Session pruning (configurable max age and count)
  • Resume with --resume or --session <id>

MCP Integration

The Model Context Protocol (MCP) allows extending Automergent with external tool servers. Configure MCP servers in your config:

yaml 
mcp:
  servers:
    my-server:
      command: "npx"
      args: ["-y", "@my/mcp-server"]
      env:
        API_KEY: "xxx"
