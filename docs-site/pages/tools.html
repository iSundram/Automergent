Tools Reference

Automergent exposes 36+ built-in tools organized by category. Each tool is self-documenting: the model receives its metadata, usage guidance, and examples automatically from the live registry. This page is a human-readable reference for all of them.

How Tools Work

Tool Registry

Every tool is registered in a global tools.Registry at startup. The registry is thread-safe and supports cloning for sub-agent isolation. Tools provide a ToolMeta struct that documents itself: display name, category, when to use, when not to, examples, and per-model-family tuning.

Auto-documentation

Tool documentation is assembled from the LIVE registry every turn. RenderToolSections() groups tools by category, orders them deterministically (by category rank, inject order, then name), and renders each tool's metadata. Newly registered tools are documented automatically — no manual prompt maintenance required.

Execution Flow
  • The model emits a tool call with name and JSON arguments
  • The orchestrator looks up the tool in the registry
  • Arguments are coerced and validated against the tool's schema
  • Confirmation is checked (if required in current mode)
  • The tool executes and returns a Result (content + summary + metadata)
  • Output is truncated or ghosted if it exceeds limits
  • The result is appended to the conversation for the model to continue
Cost Estimation

Each tool provides an EstimatedCost() returning token approximation, typical latency, and risk level (low/medium/high). The orchestrator uses these to budget tool calls and prioritize cheaper tools when possible.

Confirmation System

How It Works

Tools declare whether they require confirmation via RequiresConfirmation(mode). The mode is the current agent phase (plan, edit, act). In plan mode, all mutating tools require user approval. In edit mode, write operations require approval. In act mode, most tools execute immediately.

Confirmation Behavior
  • Read-only tools (read_file, glob, grep): Never require confirmation
  • Write tools (write_file, edit_file): Require confirmation in edit/plan modes
  • Shell tools (bash): Require confirmation in plan/edit modes
  • Agent tools (task): Never require confirmation (they manage their own lifecycle)
User Override

When a confirmation dialog appears, the user can approve, reject, or provide feedback. Rejected tools return an error result that the model can react to. The user can also configure auto-approval for specific tools.

Per-tool Permissions

Configuration

You can configure per-tool permissions to control which tools the agent can use without confirmation. This is useful for automating repetitive tasks while keeping dangerous operations gated.

Commands
/permissions add <tool> # Allow tool without confirmation
/permissions remove <tool> # Restore confirmation requirement
/permissions list # Show current permissions
Examples
/permissions add read_file # Auto-approve all reads
/permissions add bash # Auto-approve shell commands
/permissions remove bash # Require confirmation for shell again
Tip: Start restrictive and add permissions as you trust the agent. Read-only tools are safe to auto-approve. Shell and write tools should require confirmation for new projects.

Tool Output Handling

Max Output

Tool output is bounded to prevent context window overflow:

  • read_file: Max 10,000 lines per call; use start_line/end_line for large files
  • bash output: Preserved to file (up to 5 GB); RAM buffer capped at 256 KB
  • grep: Results truncated at configurable limit
  • web_fetch: Body capped at 512 KB
  • secrets_scan: Max 100 findings per scan
Ghosting

When tool output exceeds a threshold, it is "ghosted" — a summary replaces the full content, with a pointer to the full output file. This keeps the context window manageable while preserving access to complete data.

Shell Output Files

Each async shell session writes output to ~/.automergent/shells/{id}.log. The RAM buffer holds only the last 256 KB. read_shell returns only new output since the last read, and points at the full file when the buffer was trimmed.

Security & Sandboxing

Blocked Write Paths

The configuration supports blocked_write_paths — directories where write_file, edit_file, multi_edit, and notebook_edit refuse to write. This protects critical system files, config directories, and vendor code.

Allowed Write Paths

When allowed_write_paths is set, ONLY those paths can be written to. This is a whitelist mode for maximum restriction — the agent can only modify files in specified directories.

Shell Sandboxing
  • Commands run in their own process group for clean termination
  • Sensitive environment variables (API keys, tokens) are stripped
  • Compound commands run sandboxed per policy
  • The size watchdog kills sessions exceeding 5 GB of output
  • The stall watchdog detects interactive prompts and advises the model
Web Fetch Protections
  • DNS rebinding protection: resolves once, validates all IPs
  • Blocks private/loopback/link-local addresses
  • Blocks cloud metadata endpoints (169.254.169.254)
  • Content-type allowlist (text/*, application/json, etc.)
  • Max redirect chain: 10, each validated
  • Body capped at 512 KB
File Reads
  • Symlinks are refused (TOCTOU protection via O_NOFOLLOW)
  • Binary files are detected and refused
  • Diagnostics are run pre-write to block error-introducing changes
Tip: Configure blockedWritePaths in your .automergent/config.yaml to protect sensitive directories. Start with the defaults and tighten as needed for your project.
