Sub-agent System Stable

Automergent spawns specialized child agents to parallelize work. Each sub-agent runs in its own context with an isolated tool registry and todo store, reporting progress back through a steering channel.

Agent Types

general-purpose

Default

Full capabilities — file editing, code generation, debugging, refactoring. Use when the task requires writes or multi-step reasoning.

task(agent_type="general-purpose",
     prompt="Implement the OAuth2 flow in src/auth.ts")

explore

Read-only

Fast, read-only agent for locating files, grepping patterns, and understanding code structure. No write tools available.

task(agent_type="explore",
     prompt="Find all database migration files")

review

Analysis

Specialized for code review, bug detection, and security analysis. Produces structured findings with severity levels.

task(agent_type="review",
     prompt="Review src/api/handlers.go for security issues")

contexter

Memory

Context management and compaction. Optimizes memory usage by summarizing long conversations and managing context windows.

task(agent_type="contexter",
     prompt="Compact the session history for topic X")

coordinator

Orchestrator

Spawns and manages other agents. Decomposes complex tasks, assigns sub-agents, and aggregates results.

task(agent_type="coordinator",
     prompt="Refactor the payment module: explore, plan, implement")

task

Shell

Executes shell commands with verbose output. Ideal for build, test, and deployment tasks that need terminal access.

task(agent_type="task",
     prompt="Run the full test suite and report failures")

Spawning Agents

Use the task tool with a self-contained prompt. The parent agent should include all necessary context since the child has no access to parent conversation history.

// Self-contained prompt — child agent cannot see parent context
task(
  agent_type="explore",
  prompt="""
    Project: Automergent CLI
    Goal: Find all error handling patterns in Go source files.
    Constraints: Read-only, no modifications.
    Output: List files with line numbers and the pattern used.
  """
)
Tip Always include project context in the prompt. Sub-agents start with a blank slate — they only see what you provide.

Parallel Execution

Launch multiple agents simultaneously with batch_task. Each runs independently, and results are collected when all complete.

// Launch 3 explore agents to analyze different parts of the codebase
batch_task([
  { agent_type: "explore",  prompt: "Analyze src/auth/ — patterns, dependencies" },
  { agent_type: "explore",  prompt: "Analyze src/api/ — routes, middleware" },
  { agent_type: "explore",  prompt: "Analyze src/db/ — models, migrations" },
])

Execution flow:

Parent agent
→
batch_task()
→
3 × explore
→
Results aggregated
→
Parent continues

Background Execution with Live Progress

Sub-agents run in the background. The parent agent continues working while children execute. Task notifications arrive through the steering channel:

// Parent receives notifications like:
// [task:explore] Completed in 12.3s — found 47 files, 3 patterns
// [task:review]  Completed in 8.1s  — 3 warnings, 0 errors

// Read results when ready:
read_agent(agent_id="task-explore-001")

Per-child Tool Registry & Todo Store

Each sub-agent maintains an isolated workspace:

Isolation BoundaryWhat's Isolated
Tool RegistryEach child only has tools matching its agent type (explore gets read-only tools, task gets shell tools)
Todo StoreEach child's task list is independent — no cross-contamination
Context WindowEach child has its own LLM context — parent context is not inherited
Memory ScopeChild agents cannot modify parent memory — only report findings

MCP — Model Context Protocol Stable

MCP is a standard protocol for integrating external tools and resources into Automergent. It lets you connect custom APIs, databases, and services as first-class tools.

Server Configuration

Add MCP servers in config.yaml:

# config.yaml
mcp:
  servers:
    github:
      transport: stdio
      command: "npx"
      args: ["-y", "@modelcontextprotocol/server-github"]
      env:
        GITHUB_TOKEN: "${GITHUB_TOKEN}"

    postgres:
      transport: sse
      url: "http://localhost:8080/mcp"
      auth_token: "${DB_TOKEN}"

    filesystem:
      transport: stdio
      command: "npx"
      args: ["-y", "@modelcontextprotocol/server-filesystem", "/safe/path"]

Transport Types

TransportProtocolUse CaseHot-Reload
stdio stdin/stdout Local processes, CLI tools Restart on config change
sse Server-Sent Events Remote servers, long-lived connections Reconnect on config change
http Streamable HTTP (JSON-RPC) Remote servers with streaming Re-init on config change

Commands

CommandDescription
/mcpShow all configured MCP servers and their status
/mcp toolsList all tools provided by connected MCP servers
/mcp enable Enable a disabled MCP server
/mcp disable Disable a running MCP server
/mcp addInteractively add a new MCP server
/mcp remove Remove an MCP server from config

MCP Tools

Once connected, MCP tools are available alongside built-in tools:

// List all resources exposed by MCP servers
list_mcp_resources(server="github")

// Read a specific resource
read_mcp_resource(server="github", uri="github://repo/owner/name")

Hot-Reload Support

MCP servers support hot-reload. Edit config.yaml and changes take effect within seconds:

// Config watcher detects changes:
// [mcp] Config changed — reloading github server...
// [mcp] github: connected (3 tools, 12 resources)

Example: Adding a Custom MCP Server

# 1. Create a minimal MCP server
cat > my-mcp-server.js << 'EOF'
const { Server } = require("@modelcontextprotocol/sdk/server");

const server = new Server({ name: "my-tools", version: "1.0.0" });

server.tool("get_weather", { city: { type: "string" } }, async ({ city }) => {
  return { content: [{ type: "text", text: `Weather in ${city}: 72°F sunny` }] };
});

server.connect({ transport: "stdio" });
EOF

# 2. Add to config.yaml
# mcp:
#   servers:
#     weather:
#       transport: stdio
#       command: node
#       args: ["my-mcp-server.js"]

# 3. Verify
# /mcp tools → lists "get_weather"

Workflows Stable

Workflows are declarative YAML specs defining multi-step pipelines. Each step has an id, a prompt (with ${step-id} variable interpolation), optional dependsOn for DAG ordering, optional agentType and model overrides. The engine runs steps in dependency order with configurable concurrency and a token budget cap.

Format

Store workflows as YAML files in .automergent/workflows/:

# .automergent/workflows/deploy-check.yaml
name: deploy-check
description: Full CI pipeline before deployment
budget: 500000
concurrency: 2
steps:
  - id: lint
    prompt: "Run lint and typecheck. Report any errors."
  
  - id: test
    prompt: "Run unit tests with coverage. Fail if coverage drops below 80%."
    dependsOn: [lint]
  
  - id: build
    prompt: "Run build. Confirm output exists at dist/."
    dependsOn: [lint]
  
  - id: deploy-preview
    prompt: "Deploy to preview. Return the preview URL."
    dependsOn: [build, test]
  
  - id: smoke-test
    prompt: "Fetch the preview URL and verify HTTP 200."
    dependsOn: [deploy-preview]

Running Workflows

/workflowList all available workflows
/workflow deploy-checkRun the deploy-check workflow
/workflow deploy-check --bgRun in background with dock display

Each workflow run is logged. Access history with:

  • Click any step in the dock to see full output

Skills System Stable

Skills are specialized instructions and workflows loaded contextually. They provide domain-specific guidance without polluting the main context.

Skill Paths

LocationScopePriority
.automergent/skills/Project-specificHigher (project takes precedence)
~/.automergent/skills/User-wideLower (global defaults)

Skill Discovery & Loading

Automergent discovers skills on startup and when the /skills command runs. Skills are loaded on-demand when a task matches their description.

# .automergent/skills/testing.md
---
name: testing
description: Best practices for writing and running tests in this project
triggers:
  - "write tests"
  - "test coverage"
  - "unit test"
---

## Testing Guidelines

- Use Vitest for unit tests
- Place tests adjacent to source: src/foo.ts → src/foo.test.ts
- Aim for 80% coverage on new code
- Mock external APIs with MSW
- Use describe/it/expect pattern

The /skills Command

# Browse available skills
/skills

# Output:
# Available Skills:
#   testing     (.automergent/skills/)  — Test writing best practices
#   security    (.automergent/skills/)  — Security review checklist
#   rust        (~/.automergent/skills/) — Rust idioms and patterns
#   python      (~/.automergent/skills/) — Python conventions

Creating Custom Skills

Skills are Markdown files with YAML frontmatter:

  • name — identifier
  • description — when to load this skill
  • triggers — keywords that auto-activate the skill
  • Body — instructions, examples, constraints

Memory System Stable

Durable memory persists facts, decisions, and preferences across sessions. Memory is injected as context — not as commands — so the agent uses it as background knowledge.

Commands

CommandDescription
/memory add "fact"Store a durable fact, decision, or preference
/memory remove Delete a specific memory by ID
/memory clearClear all stored memories
/memory listDisplay all stored memories with IDs

Memory Examples

# Store a fact
/memory add "This project uses PostgreSQL 16 with Prisma ORM"

# Store a preference
/memory add "Always use kebab-case for CSS class names"

# Store a decision
/memory add "Decided to use Zustand over Redux for state management (simpler API)"

# List all memories
/memory list
# [1] This project uses PostgreSQL 16 with Prisma ORM
# [2] Always use kebab-case for CSS class names
# [3] Decided to use Zustand over Redux for state management

Dream Mode — /dream

The /dream command consolidates session memory. It reviews the current conversation, extracts durable facts, and stores them:

# At end of a productive session
/dream

# Automergent:
# Scanning session... found 4 durable facts:
# [1] API uses REST, not GraphQL
# [2] Auth middleware at src/middleware/auth.ts
# [3] Tests require DATABASE_URL env var
# [4] Build command is make prod
# Stored 4 memories. Use /memory list to review.

Auto-recall in Later Sessions

Memories are automatically injected into new sessions as background context. The agent sees them as knowledge, not instructions:

// System prompt automatically includes:
// Durable Memory:
// - This project uses PostgreSQL 16 with Prisma ORM
// - Always use kebab-case for CSS class names
// - Decided to use Zustand over Redux
Memory as Context, Not Commands Memories are injected as background knowledge. They inform the agent's decisions but don't override explicit instructions in the current prompt.

Best Practices

  • Store facts: "This project uses X", "The API endpoint is /v2/users"
  • Store decisions: "Chose X over Y because Z"
  • Store preferences: "Always use kebab-case for CSS class names"
  • Avoid storing ephemeral state — use todos for that
  • Periodically /dream to consolidate important session findings

Tool Confirmation System

Every tool invocation can require confirmation depending on your approval mode. Dangerous operations always ask:

// Always confirmed (regardless of mode):
rm -rf /
sudo anything
git push --force
DROP TABLE

Per-tool Permissions

Fine-grained control over which tools can run without confirmation:

# /permissions command
/permissions

# Output:
# Tool Permissions:
#   read_file       ✓ always allow
#   edit_file       ✓ always allow  (accept-edits mode)
#   bash            ⚠ ask each time
#   web_fetch       ✓ always allow
#   git             ⚠ ask each time

Background Shells Stable

Persistent PTY sessions that survive across agent turns. Run long-lived processes, dev servers, or watchers without blocking the main conversation.

Shell Tools

Example: Dev Server

# Start a dev server in background

Approval Modes Deep Dive Stable

Automergent offers four approval modes controlling how much autonomy the agent has. Choose based on your comfort level and task risk.

Mode Comparison

ModeFile EditsShell CommandsWeb FetchGit OperationsBest For
Manual Confirm each Confirm each Confirm each Confirm each Maximum control, sensitive repos
Accept-edits Auto-apply Confirm each Confirm each Confirm each Iterative coding, review before run
Auto Auto-apply Auto-execute* Auto-fetch Confirm push Trusted environment, rapid iteration
Plan Refused Read-only Auto-fetch Read-only Analysis only, no modifications

* Destructive operations (rm -rf, sudo, DROP TABLE) always require confirmation regardless of mode.

Per-tool Permissions

Override the mode on a per-tool basis:

# Allow bash without confirmation in accept-edits mode
/permissions allow bash

# Revoke auto-apply for edit_file
/permissions deny edit_file

# Reset to default
/permissions reset

Session-persisted Permissions

Permissions granted during a session persist until the session ends or you explicitly revoke them:

// You approve "bash" once:
// Confirm: bash "npm test" [y/n]
// y → "Remember this choice for this session?" [y/n]
// y → bash is now auto-approved for this session

Approval Flow UI

// When confirmation is needed:
┌─ Tool Confirmation ────────────────────────────┐
│ Tool:    bash                                  │
│ Command: npm test                              │
│ Mode:    accept-edits (shell requires confirm)  │
│                                                 │
│ [y] Yes, execute    [n] No, skip               │
│ [a] Always allow    [r] Remember for session    │
└─────────────────────────────────────────────────┘
Git Required for Auto Modes Auto and Full Auto modes require a clean git state (committed or stashed changes). This ensures you can always revert if the agent makes unwanted changes.
Recommended Workflow Start with accept-edits mode. Use /plan for risky changes. Upgrade to auto only after verifying the agent behaves as expected on your codebase.
