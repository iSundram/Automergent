Project: go-app — Go 1.22, module-based architecture

Directory Structure
├── cmd/           Entry points (one per binary)
│   ├── serve/
│   └── migrate/
├── internal/      Private packages
│   ├── auth/      JWT + middleware
│   ├── db/        PostgreSQL + migrations
│   └── handler/   HTTP handlers
├── pkg/           Public API packages
├── web/           Static assets + templates
├── migrations/    SQL migration files
└── deploy/        Docker + Kubernetes configs

This is a standard Go project layout following the golang-standards/project-layout conventions. Key patterns:

  • Clean Architecture: internal/ packages have no circular deps
  • Dependency injection: Constructor funcs in cmd/serve/main.go wire everything
  • Interface-driven: db.Repository interface lets handlers be tested with mocks
  • Graceful shutdown: Signal handling + context propagation
Tip: Ask follow-up questions like "How is auth handled?" or "Show me the request lifecycle" for deeper dives.

🐛 Workflow: Bug Investigation

Methodically tracing a bug from symptom to root cause.

Bug investigation: "users can't log in" Workflow
U
You
Users report they can't log in after the latest deploy. Help me investigate.
A
Automergent
✓ Bash: git log --oneline -20
✓ Bash: git diff HEAD~5..HEAD --stat
✓ Grep "auth\|login\|token" --include "*.go"
✓ Read auth/handler.go
✓ Read auth/middleware.go

Investigation log:

1. Last 5 deploys touched auth/, db/, and config/

2. git diff HEAD~5..HEAD auth/ shows the middleware was changed to require exp claim validation

3. But the token signing code in auth/token.go:45 still uses time.Now().Add(24 * time.Hour) — this looks correct

4. Checking the config…

✓ Read config.yaml

Found it. The config change in deploy/config.yaml switched token_issuer from "app" to "App" (capitalized). The middleware validates iss claim case-sensitively, so all existing tokens are rejected.

Fix: Revert the issuer value to lowercase, or make the comparison case-insensitive.

Pattern: Explore → read relevant files → identify root cause → propose fix. The agent often finds issues in config, environment, or dependency changes before touching code.

📋 Common Patterns

These are battle-tested patterns for getting the most out of Automergent.

PatternWhyExample
Read before edit Agent understands context before making changes "Read auth.go, then add rate limiting"
Grep before read Find the right file without guessing "Find where JWT validation happens"
Test after change Catch regressions immediately "Run tests after editing"
Use sub-agents for parallel work Explore multiple areas simultaneously "Launch 3 agents to analyze src/, tests/, docs/"
Monitor context with /context Prevent context overflow in long sessions "/context" after 15+ messages
Use /compact proactively Free up space before it's needed "/compact" at 60-70% usage
Plan first, then implement Get alignment before large changes "/plan Refactor the auth module"
Ask for options Agent will propose alternatives "How should I fix this? What are the options?"

Session Lifecycle

A typical well-structured session:

1 Explore — "Explore the project structure"
2 Understand — "How does auth work?"
3 Plan — /plan Add feature X
4 Implement — /artifact approve → agent builds
5 Verify — "Run tests"
6 Review — /review
7 Ship — /commit fix: description

Anti-patterns to Avoid

Don'tDo Instead
"Edit all 50 files" Edit one file at a time, or use a plan
Skipping /compact in long sessions Run /compact at 60% context usage
"Fix everything" (vague goal) Specific: "Fix the failing test in auth_test.go"
Editing without reading first Always let the agent read the file first
Not checking /context Monitor usage, compact when needed
