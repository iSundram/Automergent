Architecture & Concepts

A deep-dive into Automergent's internals — the phase-driven agent loop, layered prompt composition, context window management, tool system, sub-agent orchestration, session persistence, and sandboxing.

1. System Overview

Design Philosophy

Automergent is a terminal-native AI coding agent written in Go. It runs entirely in your command line — no Electron, no VS Code extension, no browser. This means:

  • Zero IDE dependency — works in any terminal emulator or remote SSH session
  • Sub-millisecond responsiveness — native Go binary, no JS runtime overhead
  • Works everywhere — Linux, macOS, Windows (WSL); headless servers included
  • Composable — pipe output, script interactions, integrate into CI/CD
Core Principle: Automergent brings the power of IDE coding agents (file editing, terminal access, code intelligence) directly into any terminal — with the reliability and speed of a compiled Go binary.

2. Four-Phase Agent Loop

Every user message flows through a structured 4-phase state machine. Each phase has its own tool set, step budget, prompt style, and behavioral rules. The PhaseManager controls transitions; the PhaseClassifier determines initial routing.

┌─────────────────────────────────────┐ │ USER MESSAGE │ └──────────────────┬──────────────────┘ │ ┌────────▼────────┐ │ INIT PHASE │ │ (classifier) │ │ 3-step budget │ └───┬────┬────┬───┘ │ │ │ ┌───────────────────┘ │ └───────────────────┐ │ │ │ ┌───────▼───────┐ ┌───────▼───────┐ ┌───────▼───────┐ │ EXPLORE PHASE │ │ PLAN PHASE │ │ BUILD PHASE │ │ (read-only) │ │ (architect) │ │ (implementer) │ │ 10 steps │ │ 5 steps │ │ 20 steps │ └───────┬───────┘ └───────┬───────┘ └───────┬───────┘ │ │ │ └───────────┬───────────┘───────────────────────┘ │ ┌────────▼────────┐ │ INIT (next) │ └─────────────────┘

INIT Phase — Classifier & Router

Persona: Serious, decisive. Minimal output.

Tools: bash, read_file, glob, grep, edit_file, task — no todo tools

Step budget: 3

INIT decomposes the user message into structured intents using an LLM call. It:

  • Classifies intent type (explore, implement, fix, question, etc.)
  • Routes tasks to the appropriate phase and sub-agent type
  • Answers direct questions inline without entering the loop
  • Confirms violations via the safety ladder (warn → block_imminent → blocked)
  • Produces TaskSpec objects with phase assignment and agent routing
// internal/shared/types.go
AgentPhase = "init" | "explore" | "plan" | "build"

// TaskSpec carries routing metadata
TaskSpec {
    Agent  string  // "main", "explore", "general-purpose", "review", ...
    Phase  AgentPhase  // explore | plan | build
    Type   string  // "explore", "implement", "fix", "plan", ...
    ...
}

EXPLORE Phase — Read-Only Investigation

Persona: Thorough, investigative. File:line reporting.

Tools: glob, grep, read_file, bash, list_directory — read-only only

Step budget: 10

EXPLORE is strictly read-only. It performs codebase reconnaissance:

  • File discovery and code search (glob, grep, tree-sitter AST)
  • Dependency analysis and import graph walking
  • Violation confirmation when flagged by INIT
  • Issue-suspect investigation with file:line references
  • Produces findings for the PLAN phase or BUILD phase

PLAN Phase — Architect Mode

Persona: Structured, analytical. Produces actionable plans.

Tools: read_file, write_file, bash, task, grep, glob

Step budget: 5

PLAN consumes INIT's constraints and EXPLORE's findings to produce a structured implementation plan:

  • Ordered task graph with dependencies
  • File change manifest (which files to modify, create, delete)
  • Risk assessment and rollback points
  • Can delegate research sub-tasks via task tool

BUILD Phase — Implementer + Tester + Todo Manager

Persona: Focused, pragmatic. Verify after every change.

Tools: Full set — edit_file, write_file, bash, read_file, task, glob, grep, multi_edit

Step budget: 20

BUILD is the implementation workhorse:

  • Edits files using AST-aware diffs (tree-sitter)
  • Runs tests after every change — verify before moving on
  • Manages a todo list of sub-tasks
  • When blocked, transitions back to EXPLORE for more context
  • Emits task notifications via the steering channel

3. Prompt System Architecture

The system prompt is assembled from 11+ composable layers via the PromptComposer. Each layer is independent, cached where possible, and injected in a fixed order.

Layered Composition

1 Base Model Model-specific base (bases/{model}.txt) — identity & tone
2 Platform Core Shared rules, task discipline, action care, communication style
3 Environment Working dir, git status, platform, date, model info
4 Agent Definition Per-agent custom prompt from config or agentdef
5 Phase Prompt Phase-specific mission, rules, exit criteria (phases/*.txt)
6 Behavioral Rules Phase discipline, context hygiene, verification, safety
7 Tool Prompts Per-tool guidance — only for tools offered this phase
8 Skills / MCP Available skills & MCP server instructions
9 Dynamic Init results, task progress, working areas, todo snapshot
10 Project Instructions AUTOMERGENT.md / AGENTS.md / CLAUDE.md (user msg)
11 Git Status Snapshot Compact git status block (user msg)
12 Task Notifications Sub-agent completion notifications (user msg)
13 Long-Run Nudges Transient system messages for long-running tasks

4. Context Window Management

Automergent uses a progressive degradation ladder to keep conversations within the model's context window. The CompactionPipeline operates across 6 tiers, each triggered at a different threshold.

The Compaction Ladder

Context Window Usage 0% 50% 65% 75% 85% 90% 95% 100% ├──────────────────────┼─────────┼─────────┼─────────┼─────────┼─────────┤ ┌─────┐ │GHOST│ persist large outputs to disk, replace with stub └─────┘ ┌───────────┐ │ TRUNCATE │ keep head+tail with "[truncated]" marker └───────────┘ ┌──────────┐ │ DISTILL │ LLM-summarize old file reads └──────────┘ ┌──────────┐ │ SNAPSHOT │ Master State JSON + summary └──────────┘ ┌─────────────┐ │MICROCOMPACT│ compact tool results only via LLM └─────────────┘ ┌──────────────┐ │ FULL COMPACT │ summarize + probe-verify └──────────────┘

Token Budgets & Thresholds

TierStrategyThresholdDescription
1ghost50%Persist large tool outputs (>32KB) to disk; replace with preview stub
2truncate_middle65%Keep 40% head + 40% tail of tool results; insert truncation marker
3distill75%LLM-summarize old file reads (>2 turns old, >2KB)
4snapshotEmit Master State JSON with active tasks, facts, constraints, recent arc
5microcompact90%Non-LLM compact of all but last 2 tool results
6full_compact95%Full history summarization + probe-verify for completeness
Summary Reserve: 20K tokens  |  Auto-compact Buffer: 13K (50K window)  |  Micro-compact Trigger: 55% usage

Token Estimation

Automergent uses anchor-plus-estimate token counting:

  • Anchor: After each LLM call, the provider-reported usage anchors the count
  • Estimate: Between calls, len(content) / 4 provides a fast heuristic
  • Adaptive: AdaptiveTokenCalculator learns model-specific drift and corrects estimates over time

Compaction Boundaries & Metadata Markers

Compacted sections are delimited by metadata markers that the agent can detect:

  • [DISTILLED] — LLM-summarized tool output
  • [truncated N chars] — head/tail truncation
  • [Output persisted to path] — ghosted large output
  • # Neural Context Summary — full compact summary
  • # Context Snapshot — Master State JSON injection

Post-Compact File Restore

Ghosted outputs can be restored on demand via read_file — the stub includes the persistence path. The ToolResultStore manages the on-disk ghost files and cleans up after session end.

5. Tool System

Tool Interface & Registry

// internal/tools/tool.go

Tool interface {
    Name() string
    Description() string
    Schema() map[string]any
    Execute(ctx, args) → (Result, error)
    RequiresConfirmation(mode) → bool
    IsConcurrencySafe(args) → bool
    IsReadOnly(args) → bool
    IsDestructive(args) → bool
    EstimatedCost() → ToolCost
}

ToolCost {
    TokensApprox  int     // estimated tokens consumed
    LatencyMs     int     // typical latency in ms
    RiskLevel     string  // "low" | "medium" | "high"
}

BaseTool // embeddable defaults: conservative (not concurrency-safe, not read-only)

The Tool Registry supports:

  • Clone for sub-agents: Each child agent gets a filtered copy of the registry
  • Per-phase filtering: Only tools allowed in the current phase are offered to the model
  • ToolMeta self-documentation: Tools describe themselves via Meta() for prompt injection
  • Cost tracking: Each tool reports estimated tokens, latency, and risk level

Tool Orchestrator & Security

Security Layer: The orchestrator enforces confirmation policies, path boundary checks, destructive-op gating, and concurrency safety before any tool execution.
  • Confirmation: Destructive tools require user approval (configurable: manual / accept-edits / auto)
  • Path Boundary: PathScope enforces that file operations stay within the working directory
  • Concurrency: Tools declare IsConcurrencySafe() — the orchestrator serializes unsafe tools
  • Ghosting: Large tool outputs (>32KB) are automatically ghosted to disk to protect the context window

Agent Lifecycle

Parent Agent │ ├── task(agent_type="explore", prompt="find auth handlers") │ │ │ ├── 1. Clone tool registry (filtered for read-only) │ ├── 2. Create child session (sidechain transcript) │ ├── 3. Compose prompt (own phase + behavioral rules) │ ├── 4. Execute turns (model → tools → model → ...) │ │ │ │ │ └── steer channel ← task notifications │ │ │ └── 5. Return result (or notify on background completion) │ ├── task(agent_type="general-purpose", mode="background") │ └── Runs async. Use read_agent to collect results. │ └── batch_task([explore, review]) └── Launches multiple agents in parallel. Max 8 concurrent.

Key architectural details:

  • Per-child registry clone: Each sub-agent gets its own filtered copy of the tool registry, ensuring it can only use tools appropriate for its type
  • Own todo store: Sub-agents maintain independent todo lists
  • Sidechain transcripts: Child conversations are persisted to separate files, not mixed with the parent
  • Steering channel: Parent is notified of child completion via AgentNotification hooks
  • Background execution: mode="background" runs the agent async; read_agent polls results with optional blocking
  • Fork context: inherit_context=true copies the parent's conversation as the child's starting context
  • Resume: resume_agent_id continues a previously spawned agent's conversation

7. Session Management

Persistent Transcripts

Every conversation is persisted as a JSONL transcript. Sessions survive process restarts and can be resumed.

// internal/session/session.go
Session {
    ID        string
    Title     string
    WorkDir   string
    Messages  []ai.Message
    Metadata  map[string]string
    AllowedTools []ToolApproval   // survives restarts
    TotalInputTokens  int
    TotalOutputTokens int
}

Checkpoint / Recovery

Checkpoints are atomic snapshots written to disk at configurable intervals:

  • Written atomically via temp file + rename
  • Restricted permissions (0600)
  • Index-based naming: {session_id}_cp{index}.json
  • Recovery loads the most recent checkpoint and replays from there

Undo Stack

File edits are tracked in an undo stack. The agent can revert changes on failure or user request.

Memory System

Durable Facts: The memory system stores learned patterns, conventions, and project knowledge that persist across sessions.

Session Search & Compaction

  • Search: Full-text search across session transcripts via SearchTranscripts()
  • Compaction: Old sessions are compacted via the same 6-tier pipeline
  • Migration: Schema versioning ensures backward compatibility across upgrades
  • Redaction: Sensitive content is automatically redacted in logs and exports

8. Sandboxing

Automergent wraps every shell command in an OS-level sandbox to contain damage from runaway or malicious tool executions.

PlatformMechanismCapabilitiesAvailability
Linux bubblewrap (bwrap) Namespace isolation, mount sandboxing, seccomp, network isolation, resource limits Requires bubblewrap installed
macOS sandbox-exec (seatbelt) Filesystem restriction, network filtering,itlement-based isolation Built-in on macOS
Windows noop No sandboxing — commands run without restrictions Fallback only 
// internal/sandbox/sandbox.go
Sandbox interface {
    Wrap(ctx, name, args) → (string, []string)
    WrapWithPolicy(ctx, name, args, policy) → (string, []string)
    IsAvailable() → bool
    Name() → string
    Capabilities() → Capabilities
}

Capabilities {
    SupportsNamespaces      bool
    SupportsSeccomp         bool
    SupportsCgroups         bool
    SupportsNetworkIsolation bool
    SupportsFSIsolation     bool
    SupportsResourceLimits  bool
    RequiresRoot            bool
}

Path Boundary Enforcement

The PathScope component ensures all file operations stay within the working directory:

  • Validates every file path before tool execution
  • Prevents ../../../etc/passwd style escapes
  • Checked at the orchestrator level before sandbox wrapping
  • Configurable scope (strict: working dir only; relaxed: allow parent dirs)
Defense in Depth: Sandboxing is a safety net, not the primary defense. The approval policy, path boundary enforcement, and behavioral rules form the first three layers. The sandbox catches anything that slips through.
